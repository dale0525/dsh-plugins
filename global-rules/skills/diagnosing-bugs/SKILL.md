# 疑难 Bug 与性能回退诊断

用刚性证据链替代「看几眼代码就盲猜修补」。严格按序推进，上一阶段未拿到实证不跳下一步。

## 建立紧致变红的反馈回路

在拿到一条**确定变红、命中用户原症状、秒级可自动重跑**的复现命令前，**严禁**漫无目的地读代码猜根因。

- 优先构造最紧致的自动回路（单测／集成测 → `curl`/API 调用 → CLI 快照 → 浏览器自动化 → 最小独立复现脚本 → `git bisect`；10 级阶梯构造法与偶发／性能回退变体见 `references/feedback-loops.md`）。
- 偶发故障先加压（并发／循环／固定随机种子）把复现率拉高到稳定复现。
- 若缺少必要环境、脱敏日志或临时埋点授权导致无法本地复现，立即停止盲猜，按 `~/.dsh/AGENTS.md` 核心原则 9 调用 `ask_user_question` 向用户索要缺失前提。

## 最小化复现

拿到稳定变红的回路后，逐个删减输入字段、配置项与前置步骤，直到留下的每一个要素都是承重的（删掉任意一个就变绿）。最小化本身常直接暴露根因。

## 提出 3–5 个可证伪假设

拒绝只盯第一个想到的原因（单一锚定）。基于最小复现提出 3–5 个互相区分的假设，每条必须写清**可证伪预测**（「若原因 A 成立，则观测／改动 X 应出现现象 Y，否则排除 A」）。若假设优先级高度依赖用户才掌握的业务／运维背景，用 `ask_user_question` 请用户辅助重排。

## 单变量定位与插桩

- 优先用调试器、REPL 或既有日志区分假设；确需加临时日志时，使用唯一检索前缀（如 `[DEBUG-a4f2]`）且只打在能区分假设的关键边界，每次只变一个变量。
- **性能回退不靠打日志瞎猜**：先建立稳定的耗时／内存基线，再用 profiler 或二分隔离定位真实热点。
- 面向用户的任何命令输出、堆栈与日志摘录，敏感凭据与 token 一律脱敏为 `<REDACTED>`。

## 审视缝隙、写回归测试与修复

- 先检查仓库在正确调用链上是否存在合适的测试缝隙（见 `codebase-design`）；若只剩过浅缝隙导致难以测到真实故障路径，顺手向用户报告这一结构缺陷（不顺手大重构）。
- 把最小化复现固化为自动化回归测试（确认修复前稳定变红），再做最小充分修复使新测试与原始复现回路同时变绿，并跑一次完整相关测试套件（遵守 `~/.dsh/AGENTS.md` 核心原则 6）。

## 清理收尾

- 用 `grep` 全仓检索临时调试前缀（如 `[DEBUG-`）与临时复现脚本，彻底清除零残留。
- 交付说明中清晰记录：复现方式、最终证实的根因假设、排除掉的候选假设（有价值时）、修复与回归测试结果。
