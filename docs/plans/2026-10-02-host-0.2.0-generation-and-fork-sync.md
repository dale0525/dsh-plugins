## 0. 结论摘要

1. **升级不是「装上就行」——它会让 6 个包被宿主自动禁用。** 宿主 `dsh-app-boot`
   的 `evaluatePluginCompatibility()` 逐条比对插件的 `peerDependencies` 里的
   `@deepseek-ai/dsh*` 与运行时版本；不满足且未豁免时，patch 行被
   `row.disabled = true` **静默禁用**（§2.3）。用**官方函数**在 0.2.0-rc.2 下实测：
   14 个包中 **6 个被 deny**（§2.4）。
2. **这 6 个的修复方式是把 peer 范围加上 `0.2.0-rc.2` 那一档**，不是改代码 ——
   0.1.7-rc.2 → 0.2.0-rc.2 的**宿主自身公开 API 面差异全部是增量式**（新增字段 / 新增可选参数），
   宿主自身无一处删除（§3.2，逐文件 diff 实测）；**唯一删除在 pi-ai 依赖层**（2 个字段，§3.3）。
   改 peer 范围前必须让各包**在该世代下真实构建 + 测试通过**，
   否则只是把「被禁用」换成「加载即崩」。
3. **bre 与 workbuddy 的上游新版本恰好各解决一半问题**：bre v0.5.2 的 peer 已含
   `^0.2.0-rc.2`；workbuddy v0.7.1 的 peer **精确锁定** `0.2.0-rc.2`（写死，不是范围）。
   所以这两个的同步与升世代是**同一件事的两面**，必须合并成一个批次做（§4、§5）。
4. **⚠️ openviking 的「迁移 + 同步」在 2026-09-29 已经做完了**（本计划初稿曾误判为
   未做，本次复核已纠正，纠正依据见 §6.1）。上游把插件从仓库**根**搬到
   `examples/dsh-memory-plugin/`（shared 同理），而我方在 `98290b122`（openviking）与
   `6eae96b9d`（shared）两次 merge 里**已经按「remap 提升到根」配方同步到了 v0.4.22**：
   两次 merge 的第二父（`2b6de5ef1` / `e3c8626ea`）与上游 v0.4.22 新路径**逐字节相同**
   （30/30、78/78）。**因此 §6 不再是「待做迁移」，而是「核对已落地的同步 + 归因残余差异」。**
5. **豁免（`dsh plugin allow-version`）是逃生门，不是方案**。它按
   `包名@版本` + 精确运行时版本 记账，写进 `<profile>/compatibility.json`（§2.5）。
   用它把 6 个包一次性放行，等于**跳过全部兼容性校验**，与本计划第 1 条的目的相反，
   因此只作为「某包确实来不及改」时的**临时手段**，且必须逐包登记理由。
6. **本计划不追求「版本对齐」**。上游一天 1–2 个版本，我们砍掉了大部分代码；
   同步的真实价值只是把上游在**我们保留的文件**里的 bug 修复拉进来。

### 2.1 宿主世代的真实安装位置

| 探针 | 结果 |

| 发布时间 | `0.1.7-rc.2` → 2026-09-24；`0.2.0-rc.1` → 2026-09-28；`0.2.0-rc.2` → 2026-09-29 |

`0.2.0-rc.2` 的 13 个关键子包（`dsh-client-ui-slots` / `dsh-settings` / `dsh-llm` /
`dsh-llm-pi-ai` / `dsh-api-remotes` / `dsh-attachment` / `dsh-atomic-write` /
`dsh-home-paths` / `dsh-host-webserver` / `dsh-authorization` / `dsh-fs` /
`dsh-launch-environment` / `dsh-client-ui-settings-plugins`）在 registry 上**均存在且同版本**。

### 2.2 兼容性门禁的判定依据

宿主 `dsh-app-boot/lib/index.js:286` `evaluatePluginCompatibility(manifest, exemptions, runtimeVersion)`：

- 只看 `manifest.peerDependencies`，且只挑 `@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*` 开头的键；
- 用 `semver.satisfies(runtimeVersion, range, { includePrerelease: true })` 判定
  —— **预发布版本参与范围匹配**，所以 `^0.1.7-alpha.1` **不接受** `0.2.0-rc.2`；
- `workspace:^` / `workspace:~` / `workspace:*` 三种写法等价于「当前运行时」；
- **不读 `dependencies`，也不读 `devDependencies`** —— 这是本计划最重要的一个边界：
  6 个被 deny 的包里，绝大多数把宿主依赖声明在 **peer** 而非 dev，所以 devDeps 世代
  不影响门禁，但影响**本地构建与测试能否跑通**，两者必须分别处理（§5.2）。

### 2.3 不兼容的后果（实测读源码）

| 路径 | 行为 |
|---|---|
| bundle 层加载（`lib/index.js:929`） | 不兼容的 **bundle 被 skip**，写入 `profile.skippedBundles`，由 `reportSkippedBundles` 输出 `dsh: skipping profile bundle ...` 到 **stderr**；**不致命** |
| patch 行装载（`lib/index.js:2078`） | 不兼容的**行被 `row.disabled = true`**，并在 `report(row, reason)` 里给出 `pluginCompatibilityWarning` 文本；`row.group` 一并置 false |
| `cordis:include` 间接命中 | 连同被 deny 的行一起 deny（`includedConflicts`） |

**即：升级后不会启动失败，而是「静默少了一半功能」**——这正是最危险的地方，
必须靠 §2.4 的预检把清单先算出来，不能靠启动后肉眼发现。

### 2.4 用官方函数算出的 deny 清单（本次实测）

调用宿主自己的 `evaluatePluginCompatibility(manifest, {}, '0.2.0-rc.2')`，遍历本仓 14 个包：

| 判定 | 包 |
|---|---|
| ❌ **会被 deny（6）** | `dsh-better-reasoning-effort@0.5.1`(2 peer) · `dsh-browser-agent@0.2.0`(2) · `dsh-config-manager@0.1.76`(**14**) · `dsh-desktop-agent@0.1.3`(3) · `dsh-fakeip-fetch@0.1.1`(2) · `dsh-workbuddy-connect@0.6.5`(7) |
| ✅ **兼容 / 不受约束（8）** | `all@0.5.55`(无 peer) · `dsh-agy-link@0.6.0` · `dsh-easyrewrite@2.7.1`(无) · `dsh-imagegen@2.0.1`(无) · `dsh-loop-guard@1.1.5` · `dsh-openviking@0.4.7` · `dsh-reasoning-strip@0.1.0` · `dsh-todo-goal@0.1.0`(无) |

被 deny 的 6 个里，`dsh-config-manager` 的 14 条 peer 全部是 `^0.1.0-rc.6`，
是**最重的一处**；`dsh-better-reasoning-effort` 与 `dsh-workbuddy-connect` 将由
§4、§5 的上游同步直接解决。

### 2.5 豁免通道

- 记账文件：`<profile>/compatibility.json`（`PROFILE_COMPATIBILITY_FILENAME`），
  **profile 本地**，不在包 manifest、也不在 cordis patch 里；当前 profile 无此文件。
- 键：`包名@版本` → 允许的**精确**运行时版本列表（`isExactPluginVersion` 拒绝范围与前缀）。
- CLI：`dsh plugin allow-version`（0.2.0-rc.2 的 `lib/plugin-*.js` 内实测存在该命令）。
- 判定生效点：`evaluatePluginCompatibility` 返回的 `exempted` 为 true 时，`deny` 不执行。

## 5. bre 与 workbuddy 的同步裁定

### 5.0 真实同步基线（实测，纠正「版本号即基线」的误读）

`node scripts/sync-upstream.mjs --list` 报告的「上次同步」**对四个 fork 全部等于收养点**
（bre `833c6e0c`、workbuddy `edbc41c9`、openviking `ef75e1ce`、shared `7465426d`），
即该工具**从未反映过任何一次真实同步**（成因见 §9 R5）。真实基线须从

### 6.7 初稿误判的成因（教训，供下次巡检参考）

初稿误判「openviking 未同步」，根因是**用错了巡检判据**：

1. **用 `git log --grep="git-subtree-dir: packages/dsh-openviking"` 判断「上次同步点」** ——
   该 trailer 只出现在**收养**提交里；两次 `chore(sync): ... v0.4.22` 是**普通 merge**，
   不带该 trailer。于是「最近的同步提交」被误读成收养提交，得出「从未同步」的假结论。
   **正确判据**：找 `chore(sync): <pkg> upstream <tag>` 提交，看它的**第二父**。
2. **把「与上游不同」等同于「同步没做」** —— 实际上大部分差异是我方**有意**的裁剪与改写
   （shared 的 21 个缺失、openviking 的 `lifecycle.mjs` 删除）。
   **正确判据**：差异必须**归因**（我方提交是否触碰、上游是否改过该文件），再下结论。

### 7.1 ⚠️ 两个包名在 0.2.0-rc.2 世代**已不存在**——放范围无效，必须换源

实测：对本仓全部 35 个 `@deepseek-ai/dsh*` 依赖名逐个查 registry，**只有两个没有 `0.2.0-rc.2`**：

| 旧包名 | registry 最高版本 | 0.2.0-rc.2 世代的替代 |
|---|---|---|
| `@deepseek-ai/dsh-agent-presets` | `0.1.6-alpha.2` | `@deepseek-ai/dsh-agent-preset` |
| `@deepseek-ai/dsh-client-runtime` | `0.1.1-rc.2`（2026-08-21 后停发，共 11 版） | 见下（**无同名替代**） |

宿主 `0.2.0-rc.2` 的 82 条 `dependencies` 里，这两个旧名**都已不在**，取而代之的是
`dsh-agent-preset` / `dsh-client-ui-agent-preset` / `dsh-fs-local`（均 `0.2.0-rc.2`）。

**注意机制边界**：宿主门禁是**纯 semver 字符串判定**，**从不查 registry**（`evaluatePluginCompatibility`
全文只做 peer 名过滤 + `semver.satisfies`）。所以「放上界」**确实能让门禁返回 undefined**——
实测 `^0.1.0-rc.6` → 判为 issue，`^0.1.0-rc.6 || ^0.2.0-rc.2` → `undefined`（通过）。
**即：这两条的问题不是「门禁过不去」，而是「门禁过去了，但装进来的是一个不属于该世代的包」。**
另：`peerDependenciesMeta: {optional:true}` **不能豁免门禁**（实测「可选 + 坏范围」与
「必选 + 坏范围」同样返回 issue）。

**`dsh-config-manager` 的真实影响面（实测）**：

| 位置 | 内容 |
|---|---|
| `src/client/client-types.ts:5` | `import type { ClientContext } from '@deepseek-ai/dsh-client-runtime/client'` |
| `src/client/client-types.ts:8` | `export type { ClientContext }`（转出给本包其它模块） |
| `src/client/index.ts:9` / `:79` | 从 `./client-types.ts` 取；`export function apply(ctx: ClientContext): void` |
| `package.json` L61 / L93 / L117 / L161 | `dsh.client.inject` 含该名 · devDep `^0.1.0-rc.6` · `peerDependenciesMeta` · peer `^0.1.0-rc.6` |

**正确修法：把类型源头直接指向 `@deepseek-ai/cordis`**：

```ts
import type { Context as ClientContext } from '@deepseek-ai/cordis'
```

依据：`@deepseek-ai/cordis@4.0.4` 的 `lib/types/context.d.ts` 有
`export interface Context`（:15）与 `export declare class Context`（:40），
且 `lib/types/index.d.ts` 首行 `export * from './context.ts'`。
这也**正是 0.2.0-rc.2 世代各包自己的写法**（如 `dsh-client-locale/client:7`、
`dsh-client-ui-cordis/client:2` 均为该行）。

> ❌ **不要**改成 `@deepseek-ai/dsh-client-ui-cordis/client`。该包确实存在、`exports` 也确实含
> `./client`，但那个模块**不导出 `ClientContext`**：其 `lib/types/client/index.d.ts` 全文 14 行，
> :2 是 `import type { Context as ClientContext } from '@deepseek-ai/cordis'`（**本地别名**），
> :14 是 `export declare function apply(ctx: ClientContext)`（**仅使用**）；全包无
> `export ... ClientContext`。改用它会「模块在、类型名不在」，解析失败。

**devDep 侧同样必须换源**（`package.json:93` 的 `^0.1.0-rc.6` 对 `0.2.0-rc.2` 为 false，
而该包名最高只到 `0.1.1-rc.2`，放范围无解）。`dsh-agent-presets` 同理换成 `dsh-agent-preset`。

### 7.3 peer 范围写法约定

沿用 bre 上游的「逐线并集」写法
（`^0.1.5-alpha.1 || ^0.1.6-alpha.1 || ^0.1.7-alpha.1 || ^0.1.7-rc.1 || ^0.2.0-rc.1 || ^0.2.0-rc.2`）。

**为什么用并集而不是 `>=`（本次复核修正了初稿的理由）**：初稿写「`>=0.1.5-alpha.1`
**匹配不到任何后续预发布线**」——**这个理由在宿主门禁语境下是错的**。
宿主门禁用 `{ includePrerelease: true }`，实测
`semver.satisfies('0.2.0-rc.2', '>=0.1.5-alpha.1', { includePrerelease: true })` = **true**
（不传该选项才为 false）。bre 的 `docs/compatibility-notes.md` 那句话针对的是 **npm 依赖解析**语境
（默认 `includePrerelease: false`，实测为 false）。
**真正的理由**：`>=` 会**把未来所有预发布线一并接受**（含我们从未验证过的
`0.3.x-rc.*`），而逐线并集把接受面**限定在已验证过的档位**上——这是**范围精确性**问题，
不是「能否匹配」问题。结论（用并集）不变，**理由已修正**。
