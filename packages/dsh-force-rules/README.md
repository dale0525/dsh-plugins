# dsh-force-rules — DSH 规则门禁

> 为 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（DSH）提供的规则门禁插件：把「禁用一次性子代理」「派单后不空转」「沉默必须有上限」「席位只拿到指令授权的权限」「派单路由成对声明」「动手前先拆解并写明归属」六条规范从**散文**变成**确定性机制**，另加一条派单判据注入与归属字段（六条硬门禁 + 一组注入）

**🌏 中文**

`dsh` · `dsh-plugin` · `plugin` · `subagent` · `delegation` · `rules` · `guard` · `派单` · `子代理` · `检查点`

## 简介

规范写在 `AGENTS.md` 里只是**建议**：模型可以不遵守，而且这几条各自都真实翻过车。

| 规范 | 光靠散文的后果 |
|---|---|
| 禁用一次性子代理 | 在 dsh 0.2.0 上 `run_in_background: false` 是进入一次性路径的**唯一开关**，返回的 `runId` 无法用 `send_message` 续期，结算也不会通知派单方 —— 派单方只能同步阻塞到执行上限。0.2.1 已删掉该参数与那条路径 |
| 派单后不空转 | Root 反复查询状态或自造 sleep 陪跑，属无谓空转 |
| 沉默必须有上限 | 席位异常死掉、`subagent/end` 永不触发时，派单方**永远等不到** |
| 席位默认只读 | 派单指令里写着「只读」，子代理照样能 `write`、`git push`、发版 —— 授权范围只活在散文里，没有任何东西在拦 |
| 派单的路由必须写完整 | `provider` 与 `model` 是一个整体，只写一半识别不出任何路由。省略两个是合法的：宿主继承父会话的路由（已实测） |
| 动手前先拆解并写明归属 | 不写待办清单就没有「工作线」，也就没有哪条可以交出去 —— 整件事默认单线程跑到底，而模型看不到这有多贵 |

本插件把这些规范落成四层机制：

- **前两条规范 → 派单前拒绝**。挂在 `tools/pre-execute` 上，在工具体执行**之前**就把 `run_in_background: false` 挡回去（0.2.1 起宿主没有这个开关，该门禁自然不再触发）。这也覆盖 `run_code` 里的 `tools.subagent(...)` 子派发 —— 它走的是同一条策略流水线。
- **第三条规范 → 自唤醒检查点**。席位一启动就在派单方会话上登记一个 **60 分钟**的持久化检查点；席位正常结算就把它删掉，静默死掉就由它到点唤醒。**沉默因此有了上限。**
- **第四条规范 → 按指令授权的权限档案**。派单指令开头的标记决定席位能调哪些工具，逐次调用在 `tools/pre-execute` 上校验。该要求同时被追加到派单工具**自己的描述**上（见下节）。席位继续派单时也走同一条校验：子席位拿到的授权只能与自身同级或降为只读。
- **第五条规范 → 派单的路由必须写完整**。判据取工具**自己的参数声明**：只有声明了 `provider` 或 `model` 的派单工具才受这条约束（`subagent` 声明，`subagent_fork` 不声明，所以后者不拦）。`provider` 与 `model` 视为**一个整体**，只写一半即拒绝；**两个都不写是合法的**，宿主让席位继承父会话的路由。`reasoning_effort` 不作要求。**判据已按实测收紧过一次**：原版要求每次派单都写明路由，524 个会话里拦下 25 次，而关掉门禁的实测表明省略时继承的正是父路由——那条要求挡的是不存在的故障，已撤回，详见下文「派单路由门禁」。
- **第六条规范 → 拆解要求 + 成本读数**。拆解要求被追加到 `todo_write` **自己的描述**上：每条待办必须写明归属，一整份全是自己的清单等于宣称整件事是一条线程。同时每 4 步注入一条本轮成本读数（工具调用数、已返回字符数、最大单次结果、未完成待办数），因为它回答的是模型看不见的那个量。**实测依据**：一个 25 分钟会话里模型耗时 846 秒、推理从每步约 220 字符涨到约 9000 字符反复重推同一批未决问题，而唯一让它当场定案的输入是一行经过时长；成本读数是同一个杠杆，只是换了个被计量的量。
- **第七条规范 → 派单判据放进宿主自己的派单槽位**。宿主为派单提示预留了 runtime-context 槽位（`SUBAGENT_DELEGATION`，每步重新装配），当前只填一句「深度已达上限，别再派了」——**只说何时停，从不说何时开始**。本插件往同一槽位补正向判据，并在本轮确有花费时指名仍归自己的待办行。放在这里而非待办描述里的理由：341 个会话实测，**264 个从未写过待办**，写在待办描述上的要求到不了它们。
- **归属是声明字段，不是文本前缀**。`todo_write` 在 agent 自己的作用域内被重新注册（宿主允许作用域注册顶替同名全局工具），`items` 增加必填 `owner: "root" | "seat"`。**实测依据**：`[seat: <label>]` 文本前缀在 341 个会话中出现 **0 次**——前缀是要记得写的东西，必填字段是要填的东西。宿主的 `todo/write` 快照形状不变，归属存在旁路表里，由派单槽位读取。

> **回复与提问怎么写不归本插件管**：那是 `~/.dsh/AGENTS.md` 的散文规范，理由见「这里不做什么：回复规范不在这层」。

## 怎么识别「派单工具」

不能按工具名硬编码，也不能只看 `run_in_background` 这个参数名：`bash`、`pwsh`、`workflow` **也**声明了这个参数，但它们根本产生不了席位。

判据取工具**自己的输出声明**：只有输出 schema 的 `properties.kind.const`（或 `oneOf`/`anyOf`/`allOf` 分支里的同一位置）为 `continuable` 或 `activation`，且参数声明里有 `prompt`，才认作派单工具。不递归扫描任意位置的同名常量，也不按工具名硬编码；否则一个输出里碰巧带 `activation` 字符串的无关工具会被误判，席位就能借它绕过授权档案的白名单。

判据认两个常量：dsh 0.2.0 的 `continuable`（当时 `oneOf` 里还有一个一次性 `background` 分支），以及 dsh 0.2.1 的 `activation`（那时一次性路径已被宿主删除，每次派单都起一个独立管理的子代理）。两个都认，是因为 npm 的 `latest` 仍指向 0.2.0，而本包没有自己的宿主世代约束。

路由门禁再叠一层判据，取工具**自己的参数声明**：输出带上述常量且参数里声明了 `provider` 或 `model`，才检查路由是否写完整。

一次性禁令也只看工具自己的参数声明：参数里仍有 `run_in_background` 才拦。0.2.1 已把这个参数和那条路径一起删掉，此时同一条规则由宿主自身满足，插件不再拒绝一个工具根本没有的参数。

| 工具 | 有 `run_in_background` | 输出声明席位 | 声明 `provider`/`model` | 是否拦截 |
|---|---|---|---|---|
| `subagent`（0.2.0） | 是 | `continuable` | 是 | **两条门禁 + 描述追加标记要求** |
| `subagent_fork`（0.2.0） | 是 | `continuable` | 否 | **一条门禁 + 描述追加标记要求** |
| `subagent` / `subagent_fork`（0.2.1） | 否 | `activation` | 是 / 否 | **仅成对路由门禁（`subagent`）+ 描述追加标记要求** |
| `bash` / `pwsh` / `workflow` | 是 | 否 | 否 | 放行 |
| 未注册工具 | — | — | — | 放行 |

席位发起派单工具时，同一条 `tools/pre-execute` 决策会按「派单授权档案」校验子席位声明的等级与路径；其余工具仍按授权档案的白名单校验，两条路径不会互相绕过。上表的「是否拦截」列只列 root 发起时适用的两条门禁，席位调用 `workflow` 仍由授权档案拒绝。

同一个判据还用于**把要求写进派单工具的描述**：插件挂在 `system-prompt/assemble` 上，在装配时给每个判为派单工具的 schema 追加标记要求。理由很直接——Root 读不到规则就守不住规则；标记要求原先只写在 `AGENTS.md` 与 `delivery-discipline` 技能里，仍被漏掉过（席位拿到散文形式的工具白名单、没写标记，被静默降为只读，直到一整轮后才在某个被拒的步骤上暴露）。工具描述是模型**决定派单那一刻**唯一在眼前的位置。只改 `description`，只改派单工具。

## 行为

```
派单（continuable）  →  subagent/start  →  清旧检查点 + 登记 60 分钟检查点
                                            ↓
                          席位结算（subagent/end）
                                            ↓
                    还有别的席位在跑？ ── 是 ──→ 保留检查点
                                            └─ 否 ──→ 删除检查点
```

检查点在派单方会话上**最多只有一个**：席位启动或结算时都从持久任务表枚举并删除本插件的检查点——固定标题或固定提示文本都能认出它，包括已触发后不再活跃的历史行和续期时被改过标题的任务——再按当前在跑的席位数决定是否重建。查找不依赖内存状态，因此重启后依然成立 —— 而重启恰恰是旧检查点会和新检查点叠加的时刻。

## 派单授权档案

写一个标记，席位就只拿到这个档案允许的工具。**不写标记 = 只读**。

| 标记 | 席位可以做什么 |
|---|---|
| （无标记） | 只读：读文件、检索、联网查资料、回报结论 |
| `[只读]` | 同上（显式写法） |
| `[审核]` | 只读 **+** 只读命令（`git status/diff/log`、`ls`、`cat`、`grep`、`terraform plan`、`kubectl get` …） |
| `[编辑: src/a.js, src/b.js]` | 只读 **+** 只写这几个文件 |

英文拼写 `[readonly]` / `[review]` / `[edit: …]` 等价。

**标记必须开在指令最前面。** 前导空白（换行、缩进）容忍，但标记之前出现任何其它文字，标记就**失效**，该席位退回只读。

| 写法 | 实际结果 |
|---|---|
| `[编辑: src/a.js] 修掉这个 bug` | 编辑档案（正确写法） |
| `\n\n  [编辑: src/a.js] …` | 编辑档案（前导空白容忍） |
| `先看这里。\n[编辑: src/a.js] 修它` | **只读** —— 标记前有文字，失效 |
| 只读指令里**提到**标记：「不要用 `[编辑: src/a.js]`」 | **只读** —— 引用不再提权（旧版会提权） |

**为什么必须锚定开头**：插件若扫描整条指令去找标记，一份只读简报只要**引用**了标记就会被提权成它本来要禁止的档案——「不要用 `[编辑: src/a.js]`」真的让那个席位能写 `src/a.js`（旧版实测）。锚定开头让引用变成惰性的，同时让「哪个标记生效」不再有歧义：只有最前面那一个。

**因此不要在指令开头引用标记本身。** 要解释规则，把说明写在标记**之后**，或**去掉方括号**（写成 `编辑: <路径>`）。

**只读档案是白名单，不是黑名单**：只有名单里的工具能用，其余一律拒绝。黑名单会让宿主以后新增的写工具被**默认放行**，而那正是这个档案要防的事。

**审核档案额外禁用 shell 连接符**（`;`、`&&`、`|`、`>`、`$()`、反引号）。只白名单首个命令词是不够的：`git status && rm -rf build` 和 `git log | sh` 都以合法命令开头。只允许**单条、无连接**的只读命令。

**编辑档案按路径后缀比对**，所以 `src/a.js`、`./src/a.js` 与绝对路径都能匹配。它是防止席位跑偏出切片的**护栏**，不是文件系统沙箱。

**PTC 模式不受影响**：`run_code` 对所有档案都放行（它是席位调用其它工具的唯一通道），但它**子派发**出去的每一次调用，走的还是同一条策略流水线，按同一个档案校验。

**席位可以继续派单**：`subagent` 与 `subagent_fork` 由席位发起时也走这条校验。子席位只能拿到同级档案或只读：只读席位只能派只读或不写标记的席位；审核席位可派审核或只读，但不能派编辑；编辑席位可派只读或编辑，且子编辑标记里的每个路径都必须按同一后缀规则仍能被父席位写入。审核与编辑互不包含——审核能跑只读命令、编辑能写文件——所以两者之间不按等级互相放行。`workflow` 不产生席位声明，仍对所有席位拒绝；它的 `agent()` 写在脚本字符串里，无法在派单前静态校验。

档案在席位启动时读一次并缓存 —— 指令在席位存活期间不会变。**Root 会话不受授权档案限制**：它没有派单方；一次性禁令与半路由门禁仍按工具声明对它生效。

## 派单路由门禁

**只管「写了一半」，不管「没写」。** 省略 `provider`/`model` 时宿主让席位继承父会话的路由——这是派单方自己的选择，不是缺陷。只写其中一个才识别不出任何路由，所以拒绝的是那种情况。

**这条门禁原本要求每次派单都写明路由，已按实测撤回。** 原判据把「省略」当作「静默跑在没选的默认值上」，实测否定了这个前提：

- 524 个会话、214 次派单里，门禁拦下 25 次「完全没写路由」，成功派单 185 次。
- 关掉门禁后实测一次不带路由的派单：成功，子会话 `request/header` 记的是 `cpa/deepseek-flash`，与父会话完全一致。
- 那次强制还逼出一次 `list_subagent_models` 查询，而它**不带参数**时的输出是 `<provider> — <显示名>`（`cpa — CPA`），与带参数时的模型行 `<provider>/<model> — <显示名>` 几乎同形。照它填 `provider: cpa, model: CPA` 得到不存在的路由，真实发生了两次。

**`provider` 与 `model` 是一个整体。** 只写一半识别不出任何路由，拒绝不是「补一个就行」，而是要求要么两个都写、要么两个都不写。

**`reasoning_effort` 不再要求。** 宿主在路由未变时继承父级档位；该模型没有档位时传了反而被拒。原先「有档位就必须写」的判据是强制写明路由的副产品，随它一起撤回。

**路由本身是否有效不归本插件判。** 探针问不出来的路由（`llm` 服务不在、provider 未注册、模型不存在）一律放行，交给宿主在派单前给出它自己更详细的诊断——同一个事实不设第二个裁判，避免两条路径给出互相矛盾的报错。

| 调用 | 结果 |
|---|---|
| `subagent` 不写 `provider`/`model` | **放行** —— 继承父路由（已实测） |
| 只写 `provider` | **拒绝**（路由是一个整体） |
| 只写 `model` | **拒绝**（同上） |
| `model` 写成 `"   "` | **拒绝**（空白不是路由） |
| 写了 `provider`+`model`，没写 `reasoning_effort` | **放行** —— 宿主继承父级档位 |
| `provider`/`model`/`reasoning_effort` 齐全 | **放行** |
| `subagent_fork`（不声明路由参数） | **放行** —— 没有路由可写 |
| `list_subagent_models`（声明路由参数，但不是派单工具） | **放行** —— 查路由不该先写路由 |

派单工具的描述上只追加**授权标记**要求，不再追加路由要求。原先那句 `MUST name the child route` 连同它指向的 `list_subagent_models` 一起移除：它把一个可选字段说成必填，代价是 25 次被拦的派单。

## 这里不做什么：回复规范不在这层

「说人话」「怎么回复」这类要求是**散文规范**，唯一真源是全局 `~/.dsh/AGENTS.md` 的「沟通与回复」节，由系统提示在**每一步**送到模型眼前。

本插件曾在 `agent/turn-stopping` 上 steer 一段说人话规范。它确实能覆盖「回答即将发出」这个时刻，但代价不可接受：该事件在轮次**即将关闭**时才派发，此时回答已经写定，要改就必须让模型**再走一步**——于是**用户每条回复都会读到两条消息**，第二条才是按要求重写的版本。系统的提示词已经覆盖了同一件事，且不需要这多出来的一步。

| | 挂在轮次边界逐步重写 | 写在系统提示里 |
|---|---|---|
| 覆盖时机 | 回答写定之后 | 每一步都在眼前 |
| 用户看到几条消息 | **两条** | 一条 |
| 依赖模型主动调用 | 否 | 否 |
| 额外 token | 每次 steer 一整段规范 + 一次完整重答 | 无 |

因此该机制已整体移除：`PLAIN_SPEECH_MANDATE`、`agent/turn-stopping` 监听器、按会话 + 轮次去重的 `reminded` 守卫，以及追加到 `ask_user_question` 描述上的提问要求，都不再存在。回复与提问的规范改为只写在 `AGENTS.md` 里。


## 它不做什么

- **不替你派单**，也不改写派单内容（`prompt` 原样传给席位，越权时只拒绝调用）；只往派单工具的描述上追加标记要求。
- **不检查席位是否真的还活着**：它只保证「沉默到点会唤醒你」，到点之后查 `list_agents` 并作判断是**你**的事。检查点唤醒的提示文本里写了这一步。
- **不判断路由是否真的有效**：`provider`/`model` 是否注册、effort 是否被该模型接受，都由宿主在派单前诊断。本插件只挡「没写」与「写了个空格」。
- **不在 `subagent/end` 上做补救**：那是结算之后才触发的水位线，拦不住已经发生的派单。本插件只做「事前拒绝」与「到点唤醒」。
- **不管回答与提问怎么写**：那属于 `AGENTS.md` 的散文规范（见上节）。本插件既不改写回答，也不检查它够不够通俗。

## 配置

**无配置。** 60 分钟的界限、这条禁令与三档授权档案本身就是它存在的理由，所以是源码里的常量，而不是可能和规则漂移的设置项。

## 安装

随聚合包 `@logictan/dsh-plugins-all` 一起安装；单独安装时该包声明 `dsh.bundle.patch`，由 `dsh plugin add` 加载。

## 开发

```bash
pnpm test          # node --test（84 个用例，覆盖六条规范、派单槽位与归属字段、三类误报与三档授权档案）
node build.mjs     # src/ → lib/（prepare / prepack 也会跑）
```
